# 项目固定契约

## 事实与优先级

- 项目基于 `llama.cpp`，用于全国大学生操作系统大赛功能赛道决赛。
- 用户主要负责 KV Cache；队友负责权重和专家激活；后续重点是统一预算、I/O 调度和模块融合。
- 当前状态持续变化。任何判断必须基于当前分支源码、README、docs、测试输出和 git diff。
- 历史对话仅用于了解背景，不能覆盖当前代码事实。

任务优先级：

- P0：正确性、崩溃、数据损坏、内存/并发错误、构建或演示失败；
- P1：性能、创新性、模块融合、实验可信度；
- P2：整理、体验和非关键表达。

## 人机分工

代理可以：

- 读取源码、测试、README 和 docs；
- 做静态审计和调用链定位；
- 修改与本轮目标直接相关的源码、测试、脚本或文档；
- 执行静态检查、相关构建、单元测试和短 smoke；
- 为长实验编写可复现脚本、解析器和用户执行命令。

用户负责：

- 长时间模型回归、正式性能矩阵、一小时稳定性等高耗时运行；
- `git add`、commit、push、merge、tag 和发布；
- 关键架构决策、阶段验收和最终对外表述。

不要反复询问用户是否理解 AI 政策。用户已持续参与设计、验证和审查。本仓库是竞赛私有派生项目；仍需保证用户能解释并维护所有改动。

## 工作方式

- 先定义结果和验收，再修改。
- 阶段开始时说明一次目标、主要工作和完成标准；阶段中不重复背景；阶段结束时总结证据、限制和下一方向。
- 每轮只处理一个可独立验收的核心任务。
- 不必要时不生成 patch。
- 不伪造代码、数据、运行结果、性能收益或创新点。
- 输出必须区分：已实现并验证、已实现但证据不足、尚未实现、仅供讨论。

## KV 与融合审查重点

涉及 KV Cache 时，至少考虑：

- 内存占用、碎片、分配/回收/复用；
- 数据布局与访存效率；
- active visibility、resume、prefix/shared ownership；
- swap、prefetch、量化/压缩；
- 并发、长上下文、TTFT、TPOT、TPS；
- 正确性、异常路径和失效场景。

涉及融合时，至少考虑：

- KV 与权重/专家的内存竞争；
- I/O 优先级、带宽争用和反压；
- prefetch 冲突、重复缓存和错误恢复；
- baseline、KV-only、weight-only、combined 四组对照。
