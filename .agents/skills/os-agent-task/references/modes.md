# 七种工作模式

所有模式执行 `SKILL.md` 中的轻量全局检查；高风险或连续失败任务再读取 [systemic-workflow.md](systemic-workflow.md) 并形成状态/生命周期契约。模型建议见 [model-selection.md](model-selection.md)。

## `contract`：生成任务契约

### 目标

把用户的简短需求整理成可直接交给 CC/Codex 的精简指令，不修改仓库。

### 必须包含

1. 推荐模型；
2. 目标结果；
3. 必要上下文，仅写会改变判断的事实；
4. 修改或审计范围；
5. 关键实现/审查要求；
6. 可量化验收标准；
7. 最终输出要求。

高风险任务还必须包含：

- 当前阶段门禁；
- 关键状态和不变量；
- 合法/非法转移；
- commit/rollback；
- 生命周期测试；
- 根因不明确时只能 `audit`，不得直接 `review-fix`。

### 规则

- 不重复仓库路径、分支、Git 分工等已固化规则；只有本轮例外才写。
- 不预先规定无必要的逐步实现方法。
- 必做项和可选优化分开；默认不附可选优化。
- 提示词长度以完成任务所需的最短完整版本为准。
- 若用户没有给出验收标准，根据目标补出机器可判定标准。
- 不把局部报错直接转写为修复目标；先判断是否缺少根因证据。

### 交付

只输出可复制的任务文本，必要时在前面加一句风险提示。不要附长篇解释。

## `audit`：只读源码与工程资产审计

### 目标

基于当前代码、脚本、配置、协议、diff 和原始证据，确认系统级调用链、状态生命周期、真实根因、风险和是否值得实现。

### 允许

- 读取源码、测试、README、docs、工程账本和 git diff；
- 使用 CodeGraph 辅助定位；
- 执行只读搜索和轻量诊断命令；
- 必要时运行不修改状态的短测试以证伪假设。

### 禁止

- 修改文件；
- 生成 patch；
- 把建议写成已实现；
- 仅根据工程账本、历史文档或最后一条错误下结论；
- 根因未确认时直接给出 `review-fix` 施工方案；
- 优先怀疑 parser/Harness 来回避原始 core/server failure。

### 必须执行的系统审计

1. 明确当前阶段、上一门禁和下一门禁；
2. 按时间定位首个真实错误，而非最后一个外显症状；
3. 核对 HEAD、dirty tree、binary、argv/env、默认参数、数据类型、拓扑和 capability；
4. 重建跨模块调用链、状态集合、合法/非法转移、ownership、visibility、commit/rollback；
5. 区分 core、integration lifecycle、tooling、performance 和文档问题；
6. 根因无直接证据时，列出至少两个竞争假设和一轮可区分的最小观测；
7. 判断当前测试覆盖函数级行为还是完整生命周期；
8. 给出最小修复范围，但不得把未经证明的设计写成确定方案。

### 必须回答

- 当前全局位置和阶段影响；
- 表面症状、首个真实错误和根因置信度；
- 被破坏的不变量；
- 当前事实、调用链和生命周期；
- 替代假设及证伪方法；
- 方案收益、代价、依赖和失效场景；
- 最小集成或修复位置；
- 是否建议实现；
- 实现前必须补充的证据。

### 停止条件

发现以下任一情况时停止推断并报告证据缺口：

- 关键源码、原始日志、真实 argv/env 或构建身份缺失；
- 工作树与描述冲突；
- 账本明显陈旧；
- 无法确认实际运行路径或对象实例；
- 当前解释无法覆盖完整 lifecycle；
- 同一现象存在多个无法区分的上游原因。

## `implement`：最小范围实现

### 目标

直接完成一个根因、边界和验收标准已经明确的源码任务。

### 开始前硬条件

- 确认当前阶段和阻塞门禁；
- 确认真实根因，不只复述错误消息；
- 核对上游配置和默认参数；
- 高风险任务必须形成状态/生命周期契约；
- 验收测试必须能重现原失败路径。

任一条件不满足时停止修改，输出“证据不足，需先 audit”。

### 流程边界

- 修改前确认工作区状态、相关调用链和已有工程决策。
- 只修改达成目标所需的最小文件。
- 沿用现有命名、状态提交、错误传播、日志和测试风格。
- 不因实现方便而放宽 ownership、visibility、fail-closed、commit/rollback 或默认关闭门禁。
- 同步更新直接相关测试；除非任务明确要求，不重构外围模块。
- 高风险任务优先补生命周期单测，再做早期短集成；不要先花多轮美化 parser/report。
- 执行相关 target 构建、单元测试、fixture 和无模型短 smoke。
- 全量构建、真实模型/server、strace/mincore/cgroup 和正式长测留给用户，输出精确命令和判定字段。

### 高风险测试最低矩阵

- 正常路径；
- release/reclaim 后 reuse；
- 成功 commit；
- 失败 rollback；
- 重复循环和幂等；
- 非当前事务访问；
- active/owned/shared 保护；
- 默认关闭和安全 fallback；
- 错误传播；
- 用户侧短真实路径。

### 停止条件

- 工作区已有重叠修改且无法区分；
- 目标与验收矛盾；
- 发现更高优先级 P0；
- 实现需要超出允许范围的架构变化；
- 新证据推翻原根因；
- 短验证失败且根因不在本轮修改范围；
- 为通过测试必须修改 parser/baseline/安全门禁。

### 交付

报告：

- 当前阶段和根因依据；
- 修改文件与行为变化；
- 状态/生命周期语义是否改变；
- 短验证结果；
- 用户尚需执行的证据层；
- 未确认事项和风险；
- `git diff --stat`、`git status --short`。

不得只凭短验证写“阻塞已关闭”。若本轮改变项目状态、架构或已接受决策，只输出一行工程账本更新建议。

## `review`：审查当前修改

### 目标

独立判断当前 diff 是否符合系统契约、是否遗漏上游原因和生命周期路径、证据是否充分，以及是否可进入用户侧长验证或阶段验收。

### 允许

- 读取当前 diff、相关源码、测试、原始 artifact 和工程账本；
- 执行静态检查、定向构建或短测试；
- 对照任务目标、状态契约和验收标准；
- 使用不同于实现阶段的模型做对抗式审查。

### 禁止

- 修改文件；
- 只复述实现报告或测试列表；
- 为了代码美观提出无关重构；
- 将缺少动态验证的实现判定为完全通过；
- 因 Gate PASS 忽略真实 server/model failure。

### 对抗式检查

至少完成：

1. 独立重建上游配置、调用链和状态转移；
2. 尝试一个反例或失败路径推翻实现；
3. 检查 release→reuse→commit/rollback、重复循环和默认关闭；
4. 检查非当前事务、active、ownership 和错误传播；
5. 检查测试是否真实执行关键分支；
6. 检查 runner/parser/Harness 是否改变标准来吸收 core failure；
7. 检查 diff 规模是否与目标匹配；
8. 明确现有证据层和仍需用户运行的证据层。

### 严重级别

- 阻塞：正确性、状态提交、错误传播、越界、竞态、假通过、测试口径污染、生命周期缺口；
- 非阻塞：可维护性或诊断改进，不影响本轮验收；
- 证据不足：实现可能正确，但缺少必要真实路径、失败回滚或 clean-HEAD 证据。

### 交付

先给单一结论：`通过`、`有非阻塞问题`、`有阻塞问题` 或 `证据不足`。随后列出：

- 当前阶段影响；
- 被尝试推翻的核心假设；
- 阻塞问题及不变量；
- 已有证据与缺失证据；
- 唯一最小下一动作。

## `review-fix`：定向修复阻塞项

### 目标

只修复已经由源码或原始日志确认的阻塞缺陷，不重新猜测根因，不重新设计功能。

### 前置硬条件

必须同时具备：

1. 阻塞缺陷的直接证据；
2. 首个错误点和根因链；
3. 被破坏的不变量；
4. 最小修复范围；
5. 能覆盖原失败路径的验收测试。

缺任一项时：

- 不修改文件；
- 输出“证据不足，退回 audit”；
- 给出最小证伪动作。

用户给出的审查结论也需与当前源码和 artifact 核对，不能直接当作事实。

### 规则

- 每个改动必须对应一个明确阻塞项和不变量。
- 不顺手重构、不增加可选功能、不扩大文件范围。
- 若审查结论错误或已被当前代码解决，说明并跳过，不制造改动。
- 不通过放宽 parser、baseline、ownership 或 fail-closed 获得 PASS。
- 修复后执行直接相关构建、生命周期测试和短 smoke。
- 需要真实模型回归时，只提供用户执行命令和精确字段。

### 交付

使用“阻塞项 → 根因/不变量 → 修改 → 短验证 → 尚缺证据”对应表。结论只能是：

- `代码修复已完成，真实路径尚未验证`；
- `阻塞仍存在`；
- `证据不足，未修改`；
- 只有对应真实证据已提供时才能写 `阻塞已关闭`。

## `script`：实验、回归或解析脚本

### 目标

创建可复现、可失败、可审计的 runner、parser 或回归工具；正式长运行由用户执行。

### 系统边界

- runner 只执行并记录原始事实，不写最终 PASS；
- parser 是正式 protocol verdict authority，必须 fail-closed；
- Harness 只验证短检查和选测完整性，不能替代真实实验；
- 工具失败与 core failure 分开报告，不能通过过滤或改标准掩盖 core 错误。

### 必须具备

- 参数、build/model 身份和依赖校验；
- 污染环境清理或显式记录；
- 唯一输出目录，禁止静默覆盖；
- `set -euo pipefail` 或等价严格错误处理；
- 每个 case 的命令、argv/env、退出码、HTTP 和原始日志；
- 明确 PASS/FAIL 条件，缺失字段不得假通过；
- baseline/variant 参数固定且可追溯；
- 解析器对缺失、重复、格式错误、顺序错误和身份冲突直接失败；
- dry-run 或小规模 smoke；
- 正式长测命令和结果提取命令。

### 验证

- Shell：`bash -n`，可用时再跑 `shellcheck`；
- Python：`python -m py_compile`；
- 单元测试必须实际执行关键分支，不能只做 import、源码 grep 或 py_compile；
- 使用正负 fixture 覆盖缺失、重复、跨行、错误归因和假 PASS；
- 不启动正式性能矩阵或一小时稳定性测试。

### 交付

报告脚本路径、参数、输出目录、事实记录边界、最终 verdict authority、验收逻辑、短测结果、用户正式执行命令和结果提取命令。

## `memory`：工程账本维护

### 目标

维护仓库根目录的四个长期工程文件，使代理能快速恢复项目状态，同时保持可追溯和不污染历史。

### 支持操作

- `memory init`：从 Skill 模板创建缺失文件，不覆盖已有文件；
- `memory check`：只读检查四个文件是否存在、是否与当前源码/提交/diff冲突、是否存在计划冒充完成或实验口径不完整；
- `memory update`：仅根据当前已验证事实做最小更新。

未显式指定时，按“初始化/检查/同步”语义推断。涉及写入时，必须是用户明确要求。

### 四个文件

- `PROJECT_STATE.md`：当前目标、阶段、已验证完成、证据不足、进行中、阻塞和下一门禁；
- `ARCHITECTURE.md`：稳定架构、模块职责、数据流、不变量和集成边界；
- `DECISIONS.md`：追加式技术决策，允许 supersede，不删除历史；
- `EXPERIMENTS.md`：实验协议、证据入口、结果与限制，正式结果必须有运行证据。

### 初始化

优先执行：

```bash
bash "${SKILL_DIR:-.agents/skills/os-agent-task}/scripts/init-project-ledger.sh"
```

默认只创建缺失文件。禁止静默覆盖。

### 更新规则

- 以当前源码、diff、提交和实际测试/实验原始证据为准；
- `PROJECT_STATE.md` 可替换当前快照，但必须保留证据 commit/worktree；
- `ARCHITECTURE.md` 只在结构变化已实现、review 且相应证据通过后更新；
- `DECISIONS.md` 和 `EXPERIMENTS.md` 追加新条目，旧条目失效时写 `superseded` 或 `invalid`；
- 不复制大日志，只记录路径、哈希、命令、关键指标和结论；
- 不把讨论设想写成 accepted decision，不把 dirty-tree 或未运行实验写成正式结果。

### 交付

说明更新了哪些文件、依据什么证据、哪些内容因证据不足未写入，并给出 `git diff --stat` 与 `git status --short`。
