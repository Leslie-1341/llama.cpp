# 七种工作模式

## `contract`：生成任务契约

### 目标

把用户的简短需求整理成可直接交给 CC/Codex 的精简指令，不修改仓库。

### 必须包含

1. 目标结果；
2. 必要上下文，仅写会改变判断的事实；
3. 修改或审计范围；
4. 关键实现/审查要求；
5. 可量化验收标准；
6. 最终输出要求。

### 规则

- 不重复仓库路径、分支、Git 分工等已固化规则；只有本轮例外才写。
- 不预先规定无必要的逐步实现方法。
- 必做项和可选优化分开；默认不附可选优化。
- 提示词长度以完成任务所需的最短完整版本为准。
- 若用户没有给出验收标准，根据目标补出机器可判定标准。

### 交付

只输出可复制的任务文本，必要时在前面加一句风险提示。不要附长篇解释。

---

## `audit`：只读源码与工程资产审计

### 目标

基于当前代码、脚本、配置、协议和 diff 确认真实调用链、数据流、瓶颈、风险和是否值得实现。

### 允许

- 读取源码、测试、README、docs、工程账本和 git diff；
- 使用 CodeGraph 辅助定位；
- 执行只读搜索和轻量诊断命令；
- 必要时运行不修改状态的短测试以验证假设。

### 禁止

- 修改文件；
- 生成 patch；
- 把建议写成已实现；
- 仅根据工程账本或历史文档下结论。

### 必须回答

- 当前事实和调用链；
- 主要瓶颈是否有数据支撑；
- 方案解决什么、代价和失效场景；
- 最小集成位置；
- 是否建议实现；
- 实现前必须补充的证据。

### 停止条件

发现关键源码缺失、工作树与描述冲突、账本明显陈旧或无法确认运行路径时，停止推断并报告需要的文件/输出。

---

## `implement`：最小范围实现

### 目标

直接完成一个已明确目标和验收标准的源码任务。

### 流程边界

- 修改前确认工作区状态、相关调用链和已有工程决策。
- 只修改达成目标所需的最小文件。
- 沿用现有命名、错误传播、日志和测试风格。
- 同步更新直接相关测试；除非任务明确要求，不重构外围模块。
- 执行相关构建、单元测试和短 smoke。
- 正式长测留给用户，输出精确命令和预期判定字段。

### 停止条件

- 工作区已有重叠修改且无法区分；
- 目标与验收矛盾；
- 发现更高优先级 P0；
- 实现需要超出允许范围的架构变化；
- 短验证失败且根因不在本轮修改范围。

### 交付

报告修改文件、行为变化、短验证结果、未运行的长验证、风险、`git diff --stat` 和 `git status --short`。不自动提交。若本轮改变项目状态、架构或已接受决策，只输出一行工程账本更新建议。

---

## `review`：审查当前修改

### 目标

判断当前 diff 是否正确、范围是否合理、证据是否充分，以及是否可进入用户侧长验证或阶段验收。

### 允许

- 读取当前 diff、相关源码、测试和工程账本；
- 执行静态检查、构建或短测试；
- 对照任务目标和验收标准。

### 禁止

- 修改文件；
- 为了代码美观提出无关重构；
- 将缺少动态验证的实现判定为完全通过。

### 严重级别

- 阻塞：正确性、状态提交、错误传播、越界、竞态、假通过、测试口径污染；
- 非阻塞：可维护性或诊断改进，不影响本轮验收；
- 证据不足：实现可能正确，但缺少必要测试或日志。

### 交付

先给单一结论：`通过`、`有非阻塞问题`、`有阻塞问题` 或 `证据不足`。随后列出证据和最小下一动作。

---

## `review-fix`：定向修复阻塞项

### 目标

只修复已经确认的阻塞缺陷，不重新设计功能。

### 前置输入

优先使用用户给出的审查结论；若未提供，先从当前 diff 中确认阻塞项，再开始修复。

### 规则

- 每个改动必须能对应到一个明确阻塞项。
- 不顺手重构、不增加可选功能、不扩大文件范围。
- 若审查结论错误或已被当前代码解决，说明并跳过，不制造改动。
- 修复后执行与缺陷直接相关的构建和短测试。
- 若需要长模型回归，只提供用户执行命令。

### 交付

使用“阻塞项 → 修改 → 验证”对应表，列出仍未解决项和当前是否可进入下一验证阶段。

---

## `script`：实验、回归或解析脚本

### 目标

创建可复现、可失败、可审计的脚本或解析器；正式长运行由用户执行。

### 必须具备

- 参数和依赖校验；
- 污染环境清理或显式记录；
- 唯一输出目录，禁止静默覆盖；
- `set -euo pipefail` 或等价严格错误处理；
- 每个 case 的命令、退出码和原始日志；
- 明确 PASS/FAIL 条件，缺失字段不得假通过；
- baseline/variant 参数固定且可追溯；
- 解析器对缺失、重复、格式错误字段直接失败；
- dry-run 或小规模 smoke 模式；
- 正式长测命令和结果提取命令。

### 验证

- Shell：`bash -n`，可用时再跑 `shellcheck`；
- Python：`python -m py_compile`；
- 只运行不会耗时过长的小规模 dry-run/smoke；
- 不启动正式性能矩阵或一小时稳定性测试。

### 交付

报告脚本路径、参数、输出目录结构、验收逻辑、静态验证结果、用户正式执行命令和结果提取命令。

---

## `memory`：工程账本维护

### 目标

维护仓库根目录的四个长期工程文件，使代理能快速恢复项目状态，同时保持可追溯和不污染历史。

### 支持操作

- `memory init`：从 Skill 模板创建缺失文件，不覆盖已有文件；
- `memory check`：只读检查四个文件是否存在、是否与当前源码/提交/diff冲突、是否存在计划冒充完成或实验口径不完整；
- `memory update`：仅根据当前已验证事实做最小更新。

未显式指定时，按“初始化/检查/同步”语义推断。涉及写入时，必须是用户明确要求。

### 四个文件

- `PROJECT_STATE.md`：当前目标、阶段、已验证完成、证据不足、进行中、阻塞和下一门禁；
- `ARCHITECTURE.md`：稳定架构、模块职责、数据流、不变量和集成边界；
- `DECISIONS.md`：追加式技术决策，允许 supersede，不删除历史；
- `EXPERIMENTS.md`：实验协议、证据入口、结果与限制，正式结果必须有运行证据。

### 初始化

优先执行：

```bash
bash "${SKILL_DIR:-.agents/skills/os-agent-task}/scripts/init-project-ledger.sh"
```

默认只创建缺失文件。禁止静默覆盖。

### 更新规则

- 以当前源码、diff、提交和实际测试证据为准；
- `PROJECT_STATE.md` 可替换当前快照，但必须保留证据 commit/worktree；
- `ARCHITECTURE.md` 只在结构变化已实现并核对后更新；
- `DECISIONS.md` 和 `EXPERIMENTS.md` 追加新条目，旧条目需要失效时写 `superseded` 或 `invalid`；
- 不复制大日志，只记录路径、哈希、命令、关键指标和结论；
- 不把讨论设想写成 accepted decision，不把未运行实验写成有效结果。

### 交付

说明更新了哪些文件、依据什么证据、哪些内容因证据不足未写入，并给出 `git diff --stat` 与 `git status --short`。
